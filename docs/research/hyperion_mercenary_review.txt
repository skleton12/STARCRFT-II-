히페리온 용병 로직 검토 의견
작성일: 2026-10-27

1. 내 판단

원작 용병 시스템은 계약 구매와 전투 중 병력 고용을 분리한 구조다. 히페리온에서는 캠페인 자금으로 사용 권한을 사고, 미션에서는 광물·가스와 호출 횟수를 소비한다. 우리 모드도 이 구분을 유지하는 편이 좋다고 본다.

2. 구조 정리

기본 유닛 해금 → 계약 표시 → 자금 검사·구매 → 구매 상태 기록 → 캠페인 저장·복원 → 미션에서 호출 명령 허용 → 고용소에서 분대 생산.

구매 UI, 캠페인 소유 상태, 실제 호출 명령, 분대 생산 데이터를 서로 구분해서 다루어야 한다. UI가 구매 완료로 보이는 것만으로 실제 상태 저장이나 미션 호출 연결이 완료되었다고 판단하면 안 된다.

3. 우리 모드에 대한 제안

일반 생산 병력을 용병으로 바꾸는 체계와, 계약을 통해 고용소에서 별도 병력을 부르는 체계를 명확히 구분하는 것이 좋겠다. 둘을 같은 '용병'이라는 이름만으로 연결하면 계약을 샀을 때 무엇이 달라지는지 불명확해질 수 있다.

원작 계약 ID, 해금 조건, 계약 가격, 모드 호출 유닛, 호출 명령, 분대 인원, 미션 내 비용, 횟수와 대기시간을 하나의 대응표에 정리하자. 어떤 계약에 어떤 병력을 넣을지는 사용자 결정이며 이 문서에서는 확정하지 않는다.

내 생각에는 계약 UI를 새로 만드는 것보다 기존 구매 상태가 모드의 고용소까지 정확하게 전달되는지 먼저 확인하는 편이 효율적이다. 가능하다면 원작 구매·저장 구조를 활용하고 필요한 호출 대상과 생산 데이터를 바꾸는 방법부터 검토하면 된다.

원작에 저장 함수가 있다는 사실만으로 현재 모드의 배포 구조에서도 자동 연결된다고 볼 수 없다. 히페리온 구매 뒤 미션 초기화가 상태를 복원하고 호출 명령을 허용하는지 추적해야 한다.

4. 구현 시 주의할 점

- 구매 상태와 버튼 표시용 업그레이드를 혼동하지 않는다.
- UI 구매 연출만 실행하고 자금 차감이나 소유 상태 기록을 빠뜨리지 않는다.
- 고용소를 여러 개 지었을 때 호출 횟수와 대기시간의 공유 범위를 확인한다.
- 능력 데이터의 비용 한 항목만 최종 가격으로 단정하지 않는다. 유닛 비용과 상속도 확인한다.
- 내부 ID와 화면 표시 이름이 다를 수 있으므로 이름만으로 연결을 추정하지 않는다.
- 원작 업적 처리를 그대로 이식하지 말고 프로젝트의 업적 비활성화 규칙을 따른다.

5. 다음 검증 순서

① 히페리온 구매와 캠페인 저장·복원 경로 확인.
② 미션 초기화의 용병별 호출 허용 처리 확인.
③ 원작 계약과 모드 호출 병력 대응표 작성.
④ 구매 전후, 자금 부족, 중복 구매, 미션 전환, 저장 불러오기 시험.
⑤ 고용소 두 개, 파괴 후 재건설, 호출 횟수 소진 시험.

6. 한계

이 문서는 구조에 대한 검토 의견이다. 신규 사양 승인이나 구현 완료 보고가 아니다. 현재 모드 전체의 연결 검증, Galaxy 컴파일, 실제 게임 실행은 수행하지 않았다.
